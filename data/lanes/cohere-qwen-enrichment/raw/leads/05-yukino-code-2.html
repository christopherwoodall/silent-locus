Summary

During a single agent session on 2026-10-06, the WebFetch and WebSearch tools exhibited two distinct failure modes, both pointing at the OSS-based fetch/cache proxy layer (routify-file-proxy-sg.oss-ap-southeast-1.aliyuncs.com):

  1. Intermittent HTTP 403 Forbidden on 5 of 11 WebFetch calls. The requested targets were public GitHub REST API endpoints that were verifiably reachable; the requested URLs are transparently rewritten into signed OSS temporary-object URLs, which the proxy then rejects. An immediate retry of the identical requests in a new round succeeded.
  2. Cross-request result contamination in WebSearch. A query about Go/MCP tooling returned 8 results belonging to a completely different, unrelated query (Chinese-language Bilibili content), with zero token overlap.

Both anomalies occurred within a ~20-minute window. Concurrent direct curl calls from the same machine to the same GitHub endpoints succeeded 5/5, ruling out GitHub-side rate limiting and local network issues.

Environment

  • Host: macOS (darwin/arm64), Node.js v24.16.0
  • Agent: Yukino CLI, session date 2026-10-06
  • Tools affected: WebFetch (5 of 11 calls failed), WebSearch (1 of 1 call returned contaminated results)
  • All target URLs: https://api.github.com/... (public, unauthenticated REST endpoints)

Control group (same session, same proxy path — succeeded)

  • Round 1 (3 parallel WebFetch): api.github.com/repos/robfig/cron, .../twmb/murmur3, .../mark3labs/mcp-go → all HTTP 200, correct JSON.
  • Round 3 (immediate retry of Batch A's identical 3 URLs): all HTTP 200, correct JSON.
  • Bash curl direct to api.github.com / raw.githubusercontent.com (5 calls, interleaved in time with the failures): all succeeded unauthenticated. A GitHub rate-limit 403 would come from api.github.com with a JSON body; these 403s were emitted by the OSS host itself, so GitHub-side throttling is ruled out.

Anomaly 2 — WebSearch returned another query's results

  • Query sent: cloudwego eino-ext mcp tool mark3labs mcp-go official modelcontextprotocol/go-sdk migration (num_results=8)
  • Returned: 8 results, all about Bilibili — 52pojie.cn threads (a Bilibili 4K/8K video downloader, Bilibili Google Play APK re-uploads, a bilibili-helper Chrome extension, Bilibili TV edition version archives) and Zhihu questions (Bilibili danmaku blocklists, Bilibili documentaries, "how do you evaluate Bilibili today"). Item dates ranged 2019–2026, including relative timestamps ("2 days ago").
  • Zero token overlap between the query and every returned title/URL/snippet.

This looks like the search path served a different request's cached result set (cache-key collision or request mix-up) in the same proxy/cache layer implicated by Anomaly 1. Note that silent contamination is arguably worse than a loud 403: wrong data can flow into agent reasoning unnoticed, whereas a 403 is at least detectable and retryable. The results were discarded in-session; the same research goal was accomplished via the GitHub search/issues REST API using curl.

Analysis

  1. URL rewriting. WebFetch transparently rewrites the requested URL into a signed OSS temporary object: routify-file-proxy-sg.oss-ap-southeast-1.aliyuncs.com/proxy_temp_file/production/<date>/trace_<traceId>/requestId_<requestId>/<objectHash>?Expires=...&OSSAccessKeyId=...&Signature=....
  2. Not signature expiry. Expires=1822099142 / 1822099143 / 1822099169 decode to ≈ 2027-09-28 (far future). The 403s are therefore more likely a signature mismatch, a missing object (write/read race on the temp object), or a bucket policy rejection — not expired URLs.
  3. Failures are correlated per round. In each failing round all parallel calls failed together; in successful rounds all succeeded together. This points at round-level proxy state (e.g., a bad cache node or signing-service instance serving that round) rather than per-request randomness.
  4. Retrying heals it. Re-issuing the identical requests in a new round succeeded immediately, yet the tool surfaces the 403 to the model without any internal retry.
  5. Observability nit. The error message helpfully exposes the final signed URL (that is how the proxy layer was identified), including the OSSAccessKeyId. An AccessKeyId is not a secret and pre-signed URLs are designed this way, so this is likely fine — flagged only so it can be confirmed that no session-scoped credentials ever leak through this error path.

Expected behavior

  • WebFetch of public, reachable endpoints should succeed reliably. On a transient proxy-layer 403/5xx, the tool should retry internally at least once (with a freshly signed URL) before surfacing an error to the model.
  • WebSearch results must correspond to the submitted query. On cache miss/collision, the backend should fall back to a live query instead of returning another request's cached results. Consider a sanity check (e.g., cache entries keyed/validated by the exact query string) before serving cached search results.

Steps to reproduce

Non-deterministic (intermittent proxy-layer fault). Observed sequence:

  1. Start an agent session; issue a round of 3 parallel WebFetch calls to public api.github.com endpoints → succeeds.
  2. Issue a second round of 3 parallel WebFetch calls to different api.github.com/repos/* endpoints → all 3 fail with 403 on the rewritten OSS URLs.
  3. Immediately retry the identical 3 URLs in a new round → all succeed.
  4. Later, issue 2 WebFetch calls (GitHub contents API + releases API) → both 403 again with a new trace/requestId; concurrent curl to the same endpoints succeeds.
  5. Issue a WebSearch with a technical Go/MCP query → Bilibili-related results returned.

Workaround

Fall back to Bash + curl for HTTP(S) fetches — worked 5/5 against api.github.com, raw.githubusercontent.com, and the GitHub search API during the same window.
