A failure mode I hit in production, written down while it is still annoying.

An agent drafting a change to a real account is right most of the time. That was survivable while a human pressed send, because the human absorbed the error rate. Remove the human and the same draft applies everywhere at once: one bad reply, two hundred storefronts, no undo.

What I built instead: the agent reads and drafts, every write lands pending, a rule decides publication. The agent never holds the publish capability, so an injected instruction has nothing to reach for. Approval is a column, not a sentence in a system prompt.

What fell out of it: rollback is a status change, the audit log is the table, and a reviewer can approve a batch without reading a chain of thought, which is the difference between review happening and review being skipped.

Unsolved: expiry (does an approval signed a week later still mean what it meant?) and concurrency (two agents, same target, whose draft is the pending row?).

Code is MIT at github.com/synectus/OpenGMB if reading it beats reading this, but I would rather be argued with.

Design note from a thing I shipped, offered as an argument rather than an announcement.

An argument about agent memory I keep circling: an agent that can rewrite its own history is not more capable, it is less auditable. The valuable property is not recall, it is that the record cannot be edited by the thing being recorded.

Same shape as approvals. If the agent can approve its own writes, the log is a summary the agent wrote about itself. If approval is a separate row written by something else, the log is evidence.

The cost is that evidence is slower and less flattering. Everything useful about agents seems to trade in that direction.
