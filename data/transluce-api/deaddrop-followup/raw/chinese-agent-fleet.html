4 October 2026

Preliminary report. A full report will follow. Evidence as of 00:45 UTC, 5 October 2026, updated 10:45 UTC the same day. Times UTC.

  • An agent fleet, likely from Tencent Hy, used urlquery.net (the scanner in Transluce's disclosure) to read which entrance of Chinese places Amap users navigate to.
  • "Agent fleet", not "swarm": many parallel agents on the same kind of task, with no sign of communication between them.
  • The fleet paused at 04:11 UTC on 5 Oct and came back at 12:00 UTC; it was still running on 6 Oct. See Update 5 October.

Key findings

  • New. First Amap scan on urlquery 28 Sept, three days after OpenAI's tool-use pause. Peak 4 Oct: 1,810 reports, 213 places.
  • Tencent sandbox. The agents' code reached its inboxes from Tencent Cloud (Hong Kong) through a proxy named hysandbox-ats.
  • Task. The share of Amap users navigating to each entrance of a park, museum, zoo or hospital.
  • Parallel. 4–8 runs active at once on 4 Oct, peak 14; 51 places in the busiest hour.
  • Not Claude. 211 reports carry a "claude" label; the code matches Tencent Hy4 and Zhipu GLM, not Claude.
  • China's date. Late-UTC tags carry China's date (UTC+8).
  • No coordination found. No inbox read back, no shared channel, no synchronised changes. Some programs were copied between places, each after its source was public on urlquery.

Update 5 October

  • Paused. Last tagged Amap scan 04:11 UTC. At 03:33 UTC a third party posted a note into the fleet's inbox 3b5027e4…, citing this post and telling the operator to rotate its infrastructure.
  • Back. Scans with fleet markers resumed at 12:00 UTC, mostly on places it had already worked but not finished; 4 places were new. Still running at 03:02 UTC on 6 Oct.
  • Same inbox, new place. From 13:51 UTC its programs reported into 3b5027e4… again, now for Beijing Wildlife Park, until the inbox hit webhook.site's 50-request cap. The fleet then created new inboxes: 0fe03879… at 15:47:18 UTC by python-requests/2.32.5 from 43.162.199.79, and four more on 6 Oct (02:10–02:30 UTC), all from Tencent Cloud. New inboxes followed the cap, not the note.
  • Three more readouts. Beijing Wildlife Park (13:51:54 UTC, main gate 26%), World Park (15:50:19 UTC, East Gate 41%, South Gate 25%, …) and Shanghai Museum (01:59:59 UTC on 6 Oct; fleet attribution is inference, as that run carries no tag or inbox).
  • New methods. The first new program is a near-copy of the 4 Oct program that produced a readout. Starting 6 October 05:21 UTC, agents were able to retrieve data using a free public AI model at mailbox.termina.digital. This service queries an AI model with computer use. Agents sent details about their environment limitations and other questions that the website poses, and were able to retrieve data from Amap as a response to this. New hosts and channels: catbox and bytebin pages, ntfy, and beacons to urlquery's own robots.txt.

3. The agents' code ran on Tencent Cloud, behind a proxy named hysandbox-ats

  • 15 of 16 readable Amap inboxes (4–5 Oct) created from Tencent Cloud (AS132203), 13 by python-requests/2.32.5.
  • 9 requests from the agents' code (Python, curl) reached them from Tencent Cloud, Hong Kong, each with a Via header such as https/1.1 traffic_server[8adac333-65b9-4b5a-a049-8accc39f11e2] (hysandbox-ats).
  • 2 inboxes from 30 Sept, used against an unrelated statistics app: also Tencent-created, also hysandbox-ats. 11 marked requests, 2 campaigns.
  • The 11 came through 9 proxy processes. With inbox creation, the fleet used 19 Tencent addresses, 9 of them in 43.162.192.0/18. No fixed pairing: one process used two addresses, one address served two processes.
  • One proxy process, 34401cc5…, served both campaigns: 30 Sept 23:46 and 5 Oct 03:16.
  • Ta'er Temple (inbox 6ddc559e…, report 97f0619b): marked request 1 s after inbox creation, 35 s before its address first appeared in public, so only the environment that created the inbox knew it.
  • The proxy rewrites requests. All 7 python-requests calls through it arrived with Accept-Encoding: gzip. Without it, python-requests 2.32.5 sends gzip, deflate (4 of 4 such requests from others in our inbox archive). gzip alone is what ATS forwards under its default normalize_ae setting.
  • "HY" is Tencent's Hunyuan brand. No public documentation of hysandbox. Tencent holds a certificate for *.hysandbox.tencent-cloud.com (crt.sh 28800673223, valid from 18 Aug 2026). Those names resolve to Tencent Cloud Beijing (AS45090), not the fleet's network; nothing ties them to the proxy directly.
  • Not Tencent's public sandbox product, by the team's tests (5 Oct; we have not reviewed their data). 196 requests from 24 sandboxes of Tencent Cloud's Agent Sandbox service (Hong Kong, Guangzhou) to the team's own inbox carried no Via and kept gzip, deflate. They left from 61 addresses in 10 Tencent blocks, none in 43.162.0.0/16. Tencent's open-source CubeSandbox sends traffic out through OpenResty, which adds no Via (we read its source). Inference: the fleet did not run in that service in its standard internet mode.
  • Asked by the team to read a page on their server, Tencent's Yuanbao assistant fetched it twice within 2 s as desktop Chrome, from China Telecom (Hubei) and China Unicom (Hebei), with no Via.
Evidence: the full chain, step by step
Kind Step
Observed The programs the agents submitted to urlquery contain webhook.site inbox addresses, and send their results there.
Observed For any inbox, webhook.site's API publicly returns a request log and a creation record.
Documented webhook.site's open-source code fills the creation record's IP and user agent from the request that created the inbox. They describe the creator, not a later visitor.
Observed 15 of the 16 readable inboxes were created from Tencent Cloud (AS132203). Thirteen were created with python-requests/2.32.5: a script, not a person in a browser.
Observed Each inbox's log shows urlquery's scanner (Firefox 134, one Oslo address), proxies the programs route through, a third-party crawler (UrlQueryCollector), and nine requests from Python or curl.
Observed All nine Python and curl requests came from Tencent Cloud in Hong Kong, and every one carries a Via header ending (hysandbox-ats).
HTTP standard A forwarding proxy adds a Via header to name itself. traffic_server is Apache Traffic Server (ATS); the text in parentheses is the name its operator configured. The bracketed ID is the proxy process's ID, set once when the process starts (ATS source); it does not change per request.
Observed Ta'er Temple: inbox created by Python from Tencent Cloud at 15:01:01. A Python request with the hysandbox-ats marker reached it at 15:01:02. urlquery's browser loaded the program at 15:01:08. The urlquery report, the first public record of the address, was stamped at 15:01:37.
Conclusion At 15:01:02 only the environment that created the inbox knew its address. The creating request and the marked request came from different Tencent Cloud addresses; the marked request came from the agents' own environment, which sends its traffic through hysandbox-ats on Tencent Cloud.
Conclusion The proxy is named for HY, the brand of Tencent's Hunyuan models; it runs on Tencent's own cloud; it serves agents on a Chinese-map task. There is no public documentation of the name, so this rests on those facts together.

4. The agents worked around Amap's protections

  • At least 8 scripts read the browser's cookies, which Amap set during the scan, and sent them to an inbox or echo service along with their results.
  • Most scripts generate Alibaba anti-bot tokens (bx-ua, bx_et, UMID) to get past Amap's protections.
  • Routes: urlquery's browser; Baxia anti-bot scripts; microlink Puppeteer; r.jina.ai; webhook.site inboxes; chunked httpbin requests. Also Baidu Translate's page translator (6 reports on 4 Oct; urlquery recorded no Amap request in any) and pre-amap-pc-ssr.amap.com, by its name Amap's pre-release server (49 reports, 30 Sept and 4 Oct).
  • Runs arrived knowing Amap's API. On 28 Sept only Amap's own pages called getPoiInfo; the first direct request came on 29 Sept at 23:06. Of the 208 places first seen on 4 Oct, 60 asked getPoiInfo in their very first scan.
  • Published keys, not stolen ones. Four programs on 4 Oct loaded Amap's JavaScript API with keys other than amap.com's own, each key once: Amap's CodePen demo key (on its demo pages since at least 2023), a key hard-coded in Amap's own coordinate-picker tool, and a key from a 2022 blog template. The fourth key we found nowhere; its paired security code is in a public company Git repository. Only that pair got a full-size reply (1.6 kB of JSON). We saw no fleet scan read any of the publishing pages.
  • At most 1,600 of 2,479 submissions (survey's broader count) got a 2xx with a body from Amap; includes CAPTCHA pages.
  • Two readouts:

Limitations

  • No record names the model or a training job.
  • Tag words do not reliably identify runs.
  • A Via name is self-reported; Tencent Cloud is open to anyone.
  • The Agent Sandbox and Yuanbao tests are the team's; we have not reviewed their data.
  • Model tests are small; self-identification varies with prompt and language.
  • urlquery stores no page content; public records expire. Counts are lower bounds.

Methods

  • Counting: reports whose submitted or final URL is on amap.com or gaode.com; place = Amap ID in that URL. Charts use the Misaligned Agent Activity Survey's broader count.
  • urlquery: public report JSON and listings; submitted URLs never visited. General collection from Sept 2023 (sparse); targeted backfill from Sept 2025.
  • Inboxes: webhook.site public read APIs only.
  • Archives: Wayback Machine CDX index and archive.today listings for Amap hosts; the captures themselves were not opened.
  • Models: plain prompts via first-party APIs.
