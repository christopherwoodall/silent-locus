# FALSE-POSITIVES — Lane 9: Jina AI reader scanner

This file lists the noise the Jina reader scanner will see. Extracted
text is not evidence of fleet activity until an IOC pattern matches a
known fleet shape: a webhook.site UUID in a dead-drop context, a
watched ntfy topic, or a tag grammar (`uqscan=`, `uqframe=`, `zz=`)
tied to agent infrastructure.

## Jina reader artifacts (the dominant noise)

The reader injects its own chrome into extracted text: "Generated by
Jina AI Reader", markdown image placeholders `![Image N]`, and
truncated-content notices. These are reader artifacts, not page
content. The scanner does not match on them. If a future Jina version
changes its chrome, update the extraction logic, not the IOC list.

## Base64 runs in normal web content

Long base64 strings appear in ordinary pages: data-URI images,
embedded fonts, CSP hashes, JWT tokens, tracking pixels. A base64
run alone is LOW confidence by design. It becomes signal only when
it decodes to fleet-shaped content (checked via `_common.normalize`)
or appears alongside a tag grammar or dead-drop UUID.

## ntfy.sh topic collisions

`ntfy.sh/<topic>` matches any public topic mention. Most ntfy topics
are benign (CI notifications, home automation, personal alerts). A
topic is signal only if it is on the config watchlist
(`ntfy_topics`) or appears alongside fleet markers. Random topic
names in blog comments or docs are noise.

## Tag grammar in documentation

`uqscan=`, `uqframe=`, and `zz=` strings appear in writeups ABOUT
the hunt (including our own reports and the NorForge/Swarmcha.se
coverage). A tag grammar match in a security blog is the author
describing the marker, not the fleet using it. Check the surrounding
context: is the page describing the hunt, or exhibiting the
tradecraft? The scanner records the match; the triager decides.

## webhook.site UUIDs in examples

Documentation and tutorials use example webhook.site URLs, sometimes
with real-looking UUIDs. A UUID in a code sample or tutorial is not
a live dead drop. Cross-check: does the UUID appear in our dead-drop
inventory, or is it surrounded by tutorial prose?

## Reader failures are not findings

HTTP 429 (rate limit), 451 (unavailable for legal reasons), and
timeouts mean the reader could not fetch the page. The scanner skips
failed targets without marking them seen, so the next run retries.
A target that persistently fails is a coverage gap, not a clean
result. Do not treat repeated failures as "no IOCs present".

## Triage rule

Keep a hit only if an extracted IOC matches a known fleet shape:
a webhook UUID in a dead-drop context, a watched ntfy topic, or a
tag grammar in non-documentation content. Base64 runs need a second
signal. Reader artifacts and documentation mentions are cut.
